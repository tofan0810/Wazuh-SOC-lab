## I. OVERVIEW & DETECTION-AS-CODE PHILOSOPHY

### 1. Why is Phase 4 Critical for a Modern SOC?
In Phase 3, we manually demonstrated (Manual PoC) the capability to detect RDP Brute Force attacks and trigger automated responses (Active Response). However, in enterprise operational environments:
* **Risk of Detection Regression:** When SOC teams upgrade Wazuh versions, tune Sysmon configuration files, or add new XML Rules, it is common to inadvertently "break" the logic of existing rules without detection until an actual incident occurs.
* **Prohibitive Manual Testing Overhead:** Manually booting 3 virtual machines, typing `xfreerdp` commands, and squinting at logs in Event Viewer each time rules are adjusted is labor-intensive and error-prone.

**Phase 4 solves this problem definitively using Detection-as-Code principles:**
Build a closed-loop automated testing pipeline (End-to-End Regression Testing Pipeline) using Python. Whenever rules or configurations change, a single command executes end-to-end automated verification from A to Z, returning a clean `[PASS]` or `[FAIL]` verdict.

## III. STEP-BY-STEP IMPLEMENTATION & VISUAL PROOF GUIDE

### 1. Step 1: Verify Network Connectivity and Remote Management Services Across 3 VMs

Before executing automation scripts, ensure the controller machine (Windows Host) can seamlessly communicate with all 3 virtual machines via remote management protocols: **SSH** (for Linux) and **WinRM** (for Windows).

> 💡 **Why does the Windows Victim machine utilize WinRM?**
> * **Native Windows Management Protocol:** Analogous to SSH on Linux, **WinRM (Windows Remote Management - Port 5985)** is the standard remote command-line administration protocol for Windows based on the WS-Management industry standard.
> * **Automated Evidence Collection:** WinRM allows Python scripts on the Host machine to directly run background PowerShell commands on the Victim to:
>   1. Deeply query the Windows Event Log database (accurately counting Event ID `4625` by `RecordID`).
>   2. Instantly verify firewall rule states (`Get-NetFirewallRule`) generated by Wazuh Active Response.
>   3. Read local `active-responses.log` entries **without requiring manual mouse/GUI interaction** on the Victim machine.

* **Execution Environment:** PowerShell on main computer (Windows Host).
* **Commands to run:**

```powershell
ssh -o BatchMode=yes kali-vm hostname
ssh -o BatchMode=yes wazuh-vm hostname
Test-Connection 192.168.71.129 -Count 2
Test-NetConnection 192.168.71.129 -Port 5985
Test-WSMan 192.168.71.129
```

### 5. Step 5: Execute Automated Real-World Testing (Full E2E Scenario Runner)

This represents the most critical milestone, where the RDP Brute Force attack scenario, Sysmon/Windows event logging, Wazuh Rule 100001 correlation, and Active Response containment are verified in a fully automated pipeline.

* **Install WinRM control library (initial setup only):**
  ```powershell
  python -m pip install -r requirements-e2e.txt
  ```

* **Command to execute real-world test:**
  ```powershell
  python tests/e2e/scenario_rdp_bruteforce.py --windows-user socrunner --rdp-user testw --execute
  ```

#### Intelligent Architecture & Zero False-Pass Design:
1. **Baseline Snapshot:**
   * WinRM connection to Windows host: Capture the latest `RecordID` for Event 4625 (e.g., `37380`) and count current line numbers of `active-responses.log`.
   * Automatically inspect and **remove legacy Firewall rules** (if the Kali IP was blocked from a previous run) to clear the path for fresh testing.
   * SSH connection to Wazuh Manager: Record line count of `/var/ossec/logs/alerts/alerts.json`.
2. **Controlled Attack Launch from Kali:**
   * Script SSHs into Kali and executes 10 iterations of `xfreerdp` with invalid credentials, setting environment variable `DISPLAY="${DISPLAY:-:0}"` to allow execution in headless SSH sessions.
3. **Analysis Wait:**
   * Pause for 30 seconds to allow the Wazuh Agent to package logs to Manager, and for Manager to execute its frequency correlation algorithm (`frequency="5" timeframe="60"`).
4. **Independent Evidence Verification:**
   * **Windows Event Log:** ONLY count Event ID 4625 entries where `RecordID > LastRecordId` (independent of timezone or datetime formatting).
   * **Active Response Log:** Disregard historical entries; ONLY inspect newly appended lines in `active-responses.log` for `netsh.exe` and Rule `100001`.
   * **Wazuh Alerts:** Use `tail -n +<new_line>` to ONLY match Rule `100001` alerts generated in this run.
5. **Outcome Evaluation (PASS/FAIL):**
   * Must satisfy concurrently: New Events $> 0$, New Active Response $= True$, New Wazuh Alert $= True$.

## IV. TECHNICAL CHALLENGES & TROUBLESHOOTING LOG

During the development of the automated testing suite, engineering addressed 5 complex real-world challenges:

### 1. UAC Remote Restrictions & Microsoft Account Authentication (Error 8646)
* **Symptom:** When WinRM connects to Windows 10 using a personal account, the system throws `HTTP 401 Unauthorized / InvalidCredentialsError`. When attempting to change the password via command line, Windows errors with `System error 8646: The system is not authoritative for the specified account`.
* **Root Cause:** Personal accounts on Windows 10 are linked to Microsoft Accounts (online Live IDs). WinRM over NTLM does not support cloud account authentication, and Windows 10 UAC security policies restrict standard local network accounts.
* **Solution:** 
  1. Create a dedicated pure Local Administrator account for SOC automation purposes:
     ```cmd
     net user socrunner <Password> /add
     net localgroup administrators socrunner /add
     ```
  2. Enable remote WinRM access for Local Admin accounts:
     ```cmd
     reg add HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System /v LocalAccountTokenFilterPolicy /t REG_DWORD /d 1 /f
     ```

### 2. Headless X11 Display Issue when Calling `xfreerdp` via SSH
* **Symptom:** The attack command from Kali executed via SSH terminates immediately without dispatching requests to Windows.
* **Root Cause:** By default, `xfreerdp` requires the graphical display environment variable `$DISPLAY`. In non-interactive SSH sessions, this variable is missing, resulting in `failed to open display: Please check that the $DISPLAY environment variable is properly set`.
* **Solution:** Prefix the execution command with `DISPLAY="${DISPLAY:-:0}"` to attach to the existing Kali Linux desktop display.

### 3. Timezone Desynchronization in Windows Event Log Filtering (Zero False-Pass)
* **Symptom:** Checking Event ID 4625 using filter `StartTime = (Get-Date)` always returns 0 events despite the attack taking place.
* **Root Cause:** Windows Event Log stores internal timestamps in UTC (`18:xx`), whereas PowerShell evaluates against the local system clock UTC+7 (`01:xx`). Comparing timestamp strings resulted in a 7-hour forward skew.
* **Solution:** Switch to **`RecordID`** comparisons. `RecordID` is a monotonically increasing integer identifier assigned sequentially by Windows. By comparing `RecordID > LastRecordId`, the system achieves 100% accurate event matching independent of timezones or locale formatting.

### 4. Automatic Kali IP Unblocking Prior to Test Runs
* **Symptom:** Running tests back-to-back causes the runner to report `Event 4625: 0` and fail.
* **Root Cause:** The previous run's Active Response blocked Kali's IP via Windows Defender Firewall with a 10-minute (600-second) timeout. A subsequent run within this window results in packets dropped before reaching RDP port 3389.
* **Solution:** Upgrade `snapshot_baseline` to automatically detect and flush legacy Wazuh Active Response firewall rules before initiating a new test run, ensuring clean test conditions.

### 5. Manager - Indexer Connection Monitoring & `--since=6h` Log Boundary
* **Symptom:** `lab_health.py` reports `[FAIL] Manager-to-Indexer connection not found` even though the system is operating normally.
* **Root Cause:** Filebeat inside `wazuh.manager` logs `Connection to backoff(...) established` only once upon container startup. When the container has run continuously for over 6 hours, `docker compose logs --since=6h` skips this startup entry.
* **Solution:** Switch to an active real-time connectivity probe (Live Readiness Probe): directly execute `docker compose exec -T wazuh.manager filebeat test output` to perform TLS handshakes and verify connectivity directly to Indexer port 9200, with a fallback reading `--tail=2000` logs rather than bounding by time.
